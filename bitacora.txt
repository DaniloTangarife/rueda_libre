MINIRETO 1 — Kilómetro 0: repositorio y página base
------------------------------------------

¿Qué hice?
- Creé la carpeta local rueda_libre, inicialicé Git y la conecté a un repositorio público de GitHub con el mismo nombre.
- Creé la estructura inicial: index.html, paginas/, img/ (con logo y foto de portada), css/ y bitacora.txt.
- Escribí la estructura base de index.html: <!DOCTYPE html>, <html lang="es">, <meta charset="UTF-8">, <meta name="viewport">, <meta name="description">, <title> y el <body> con un <h1> y un <p> de bienvenida.
- Abrí la página con Live Server y analicé la petición del documento en DevTools (Network).
- Probé una ruta inexistente y analicé la respuesta del servidor.

Datos de la petición principal (DevTools → Network):
- URL completa:  http://127.0.0.1:5500/index.html
- Protocolo:     HTTP/1.1
- Host:          127.0.0.1
- Puerto:        5500
- Ruta:          /index.html
- Método:        GET
- Estado:        200 OK (con caché puede verse como 304 Not Modified; ambos confirman que el documento se sirvió correctamente).

Ruta inexistente:
- Probé: /promociones.html
- Estado: 404 Not Found
- Significado: el servidor no encontró el archivo solicitado en esa ruta. Es el código que indica "recurso no encontrado". (Si en su momento apareció un 500 ENOTDIR fue porque se pidió una subruta dentro de index.html; la prueba correcta para el reto es sobre una ruta que no exista en la raíz.)

Roles de HTML, CSS y JavaScript en Rueda Libre:
- HTML: estructura y contenido. Ejemplo concreto: el <h1> de la portada y la tabla de tarifas en paginas/tarifas.html.
- CSS: presentación y diseño. Ejemplo concreto: la hoja css/styles.css que aplica la paleta de la marca y tipografías de Google Fonts a las tres páginas.
- JavaScript: comportamiento e interactividad. Ejemplo concreto: el bundle de Bootstrap que hace funcionar el botón hamburguesa de la navbar (collapse) en móvil.

¿Qué aprendí?
A configurar un repositorio con Git y GitHub, a construir la estructura mínima de un documento HTML válido y a leer en DevTools cómo el navegador pide y recibe la página (método, ruta, host, puerto y código de estado).

MINIRETO 6 — Formulario de reservas
------------------------------------------

¿Qué hice?
- Dentro de <main> de paginas/reservas.html creé la sección "Formulario de reserva" con un <form action="#" method="post">.
- Agrupé los campos en tres <fieldset> con su <legend>: "Tus datos", "Tu alquiler" (tipo de bicicleta + plan + cantidad + recorrido + fecha) y "Confirmación" (comentarios + políticas).
- Asocié cada control con su <label for> y un id, y le puse name a todos.
- Botón <button type="submit"> al final del formulario.

Controles elegidos por dato:

| Dato                  | Control                                | name           |
|-----------------------|----------------------------------------|----------------|
| Nombre completo       | <input type="text">                    | nombre         |
| Documento             | <input type="text">                    | documento      |
| Celular               | <input type="tel">                     | celular        |
| Correo electrónico    | <input type="email">                   | correo         |
| Fecha del alquiler    | <input type="date">                    | fecha          |
| Tipo de bicicleta     | <input type="radio"> (3 opciones)      | tipo_bicicleta |
| Plan                  | <input type="radio"> (3 opciones)      | plan           |
| Cantidad de bicicletas| <input type="number">                  | cantidad       |
| Recorrido guiado      | <select> + <option>                    | recorrido      |
| Comentarios           | <textarea>                             | comentarios    |
| Políticas             | <input type="checkbox">                | politicas      |

Justificación de tres elecciones:
1) Correo → type="email": el navegador valida el formato antes de enviar, evitando correos mal escritos que llegaban por WhatsApp.
2) Fecha del alquiler → type="date": muestra calendario nativo y evita fechas inválidas.
3) Tipo de bicicleta → type="radio": son tres opciones mutuamente excluyentes; con name compartido solo se puede elegir una.

Verificación:
Al hacer clic en cualquier etiqueta, el control asociado recibe el foco o se selecciona (comprobado en DevTools). Todos los controles tienen name.

¿Qué aprendí?
A elegir el control HTML adecuado para cada dato, a agrupar campos con <fieldset>/<legend> y a asociar etiquetas con for/id.

Reglas traducidas a atributos:

| Campo              | Regla del cliente                      | Atributos aplicados                                                     |
|--------------------|----------------------------------------|-------------------------------------------------------------------------|

| Correo             | Obligatorio, formato válido            | type="email" + required                                                 |
| Celular            | Obligatorio, 10 dígitos, empieza por 3 | type="tel" + required + pattern="3[0-9]{9}" + minlength="10" + maxlength="10" + title |
| Fecha del alquiler | Obligatoria, 1 nov – 31 dic 2026       | type="date" + required + min="2026-11-01" + max="2026-12-31"            |

Patrones usados y por qué:
- Documento: [0-9]{6,10} → solo dígitos ASCII del 0 al 9, entre 6 y 10 posiciones. Se usa [0-9] y no \d porque \d acepta dígitos Unicode.
- Celular: 3[0-9]{9} → 10 dígitos exactos y el primero debe ser 3.
- Ambos patrones llevan title para que el navegador muestre el mensaje de formato esperado.

MINIRETO 1 — Encabezado, menú y pie con Flexbox
------------------------------------------

¿Qué hice?
- En el encabezado puse el nombre del negocio en un extremo y el menú en el otro, centrados verticalmente con flex-direction: row, justify-content: space-between y align-items: center (a partir de 768px; en móvil es flex-direction: column con align-items: center).
- Convertí la lista del menú en un contenedor flexible con gap (var(--spacing-md)); eliminé márgenes e inline-block para separarlos.
- Agregué flex-wrap: wrap al menú para que los enlaces bajen de línea cuando no quepan.
- Organicé el pie en tres bloques en fila (marca, contacto y horario), alineados arriba con align-items: flex-start y separados uniformemente con justify-content: space-between.

Comportamiento al estrechar la ventana (observado en DevTools):
- Escritorio (≥768px): marca a la izquierda y menú a la derecha en una fila; pie con tres bloques en fila.
- Móvil (<768px): marca arriba y menú debajo centrado; pie en columna apilada.

¿Qué aprendí?
A usar Flexbox para distribuir y alinear elementos en una dimensión, entendiendo flex-direction, justify-content, align-items, flex-wrap y gap, y a evitar márgenes para separar los ítems del menú.

MINIRETO 3 — Layout en dos dimensiones (Grid + Flex)
------------------------------------------

Decisiones de Flexbox vs Grid por caso:

| Caso               | Técnica  | Por qué |
|--------------------|----------|---------|
| Portada            | Grid 1fr 1fr (desde 1200px) | Dos bloques principales en filas/columnas; control claro de proporciones. |
| Galería de rutas   | Grid repeat(3, 1fr) (desde 1200px) | Tres tarjetas del mismo ancho en una fila; grid da proporciones exactas. |
| Reservas 8/4       | Grid 2fr 1fr (desde 1200px) | Proporción 2:1 explícita con unidades fr. |
| Fila del formulario| Flex (row, flex:1, gap) | Solo una dirección horizontal; flex resuelve con menos código. |
| Encabezado         | Flex (row, space-between, align-items:center) | Una dimensión: marca vs. menú. |
| Pie de página      | Flex (row, space-between, align-items:flex-start, wrap) | Tres bloques en una línea con quiebre natural en móvil. |

Verificación:
En escritorio el layout coincide con el boceto: portada en dos columnas, galería de tres rutas, reservas en proporción 2:1. Las columnas se definen con fr. El menú, la flota y la validación del formulario siguen funcionando.

Nota: tras la migración a Bootstrap (Semana 2, reto 7-8), estos layouts se resuelven con row g-4 + col-*; las reglas propias quedaron comentadas en styles.css como referencia didáctica.

MINIRETO 4 — Rueda Libre v1.5: mobile-first
------------------------------------------

¿Qué hice?
- Reorganicé css/styles.css con enfoque mobile-first: los estilos base (sin media query) describen la versión móvil en una sola columna y las media queries con min-width amplían el layout donde el contenido lo necesita.
- Base móvil: header en flex-direction: column con align-items: center; #menu con flex-wrap: wrap y justify-content: center; .portada, .galeria-rutas y .layout-reservas en 1fr; .fila-formulario en column; tablas con font-size: 0.75rem, table-layout: fixed y overflow-wrap: anywhere; img { max-width:100%; height:auto; }.
- @media (min-width: 768px): header vuelve a row con space-between; footer en row con wrap; galería a 2 columnas; fila del formulario en row; tablas con font-size: 0.95rem y mayor padding.
- @media (min-width: 1200px): portada en 1fr 1fr; galería en 3 columnas; reservas en 2fr 1fr.
- Eliminé el bloque @media (max-width: 768px) residual porque contradecía el enfoque mobile-first.

Tres problemas responsive y su solución:
1) Encabezado amontonado en móvil. Solución: base en column + gap; desde 768px row con space-between.
2) Tablas con scroll lateral en celular. Solución: table-layout: fixed + font-size reducido + overflow-wrap: anywhere en base; a partir de 768px se aumenta el tamaño.
3) Fila documento/celular desbordaba en pantallas pequeñas. Solución: base en column; a partir de 768px row con flex:1 y min-width:0.

Verificación en DevTools (modo dispositivo):
- 360px: sin scroll horizontal; contenido en una columna; header en columna; tablas legibles; footer apilado.
- 768px: header y footer en fila; galería en 2 columnas.
- 1280px: portada en 2 columnas; reservas 2:1; galería en 3 columnas.

Publicación: v1.5 publicada en GitHub Pages y probada en un celular real.

¿Qué aprendí?
A escribir CSS mobile-first con breakpoints min-width, imágenes fluidas y tablas legibles en móvil, en lugar de corregir un diseño desktop-first hacia abajo.

MINIRETO 5 — Flota en Bootstrap: primera comparación
------------------------------------------

¿Qué hice?
- Creé pruebas/catalogo-bootstrap.html con la plantilla de Bootstrap 5.3.3 por CDN (CSS y bundle JS).
- Copié el marcado de la flota (siete modelos) ajustando las rutas de las imágenes a ../img/ por la nueva carpeta.
- Reconstruí la distribución solo con la grilla: col-12 col-sm-6 col-lg-4 col-xl-3, con g-4 como gutter.
- No enlacé styles.css ni escribí CSS propio para la distribución en esta página.

Comparación CSS propio vs Bootstrap:

| Aspecto                         | CSS propio (Grid)           | Bootstrap 5.3                       |
|---------------------------------|-----------------------------|-------------------------------------|
| Líneas de CSS para la flota     | 6 líneas de grid + estilos  | 0 líneas                            |
| Clases de distribución          | .grid-flota                 | container, row, g-4, col-*          |
| Columnas por ancho              | auto-fit según espacio      | 1 / 2 / 3 / 4 según breakpoints     |
| Control de breakpoints          | Total (propios)             | Limitado a los de Bootstrap         |

Tiempo invertido: ~20 minutos.

¿Qué me dio Bootstrap sin esfuerzo?
La cuadrícula responsive sin escribir CSS, el gutter uniforme con g-4 y componentes listos (card, btn).

¿Qué control perdí?
Los puntos de quiebre y los anchos dependen de los valores del framework; personalizar exige sobrescribir variables (lo cual llegará en el reto 12).

Pruebas en DevTools (modo dispositivo):
390px → 1 columna; 768px → 2 columnas; 1024px → 3 columnas; 1280px → 4 columnas. Sin 404 en Network.

¿Qué aprendí?
Que Bootstrap reduce drásticamente el código de distribución a costa de perder control directo sobre breakpoints.

MINIRETO 7 — Inicio migra a Bootstrap
------------------------------------------

¿Qué hice?
- Agregué Bootstrap CSS + bundle JS a index.html, con css/styles.css cargado DESPUÉS para mantener la cascada.
- Reemplacé la distribución de la portada, la flota (con el marcado del reto 5), la galería de rutas y los beneficios por la grilla (row g-4 + col-*) y utilidades.
- Eliminé de styles.css las reglas de distribución que inicio ya no usa y dejé comentadas las de tarjetas, portada, galería y reservas como referencia didáctica (retos 2 y 3 de la semana 2).
- Probé inicio a 360px, 768px y 1280px en modo dispositivo: se ve correctamente en los tres anchos.

Tres conflictos detectados con DevTools y su solución:

1) Color azul por defecto de Bootstrap en enlaces del footer.
   - Diagnóstico: la regla a { color: … } de Bootstrap ganaba por orden a la regla de marca.
   - Solución: se ajustó la regla en styles.css usando la variable --bs-link-color: var(--verde-ruta); y --bs-link-hover-color: var(--verde-hover); en :root, sin !important.

2) Margen inferior rígido del selector article que desalineaba las tarjetas frente al g-4 de la fila.
   - Diagnóstico: el selector global article imponía margin-bottom: 2rem sumado al gap de la fila.
   - Solución: se aplicó la clase utilitaria mb-0 (y h-100 para altura uniforme) en las tarjetas dentro de la grilla, neutralizando el margen heredado sin tocar el selector global.

3) Tamaño y peso de encabezados alterados por Bootstrap.
   - Diagnóstico: Bootstrap redefine font-size y font-weight de h1–h6.
   - Solución: se reforzó el marcado con clases utilitarias explícitas (h3, h4, fw-bold, lead) y se mantuvo la tipografía Montserrat mediante la regla agrupada h1,h2,…{font-family: var(--font-heading)}. Las fuentes y colores de marca se mantienen.

Verificación: los tres anchos correctos; styles.css se carga después de Bootstrap; no se usó !important en ningún cambio.

¿Qué aprendí?
A resolver conflictos de cascada y especificidad con orden de carga y variables, no con !important.

Familias de utilidades usadas:
- Espaciado: px-6, py-16, pt-4, space-y-8, space-y-1, gap-8, gap-12, px-4, py-1,
  px-8, py-4.

- Colores: bg-slate-950, text-slate-100, bg-amber-400, text-slate-900,
  text-white, text-slate-300, text-slate-400, text-amber-400, bg-emerald-500,
  hover:bg-emerald-400.
- Tipografía: text-5xl md:text-7xl, text-lg md:text-2xl, text-xs, text-3xl
  md:text-4xl, font-extrabold, font-bold, font-semibold, leading-tight,
  leading-relaxed, tracking-tight, tracking-widest, uppercase.

Comparación del botón "Inscríbete": Bootstrap (Semana 2) vs Tailwind (Semana 3)
-------------------------------------------------------------------------------
Semana 2 (Bootstrap):
    <a href="..." class="btn btn-primary btn-lg">Inscríbete</a>
  → Una sola clase btn-primary trae fondo, color de texto, padding, radio,
    estados hover/focus y transición desde el framework.

Semana 3 (Tailwind, utility-first):
    <a href="..." class="inline-block bg-emerald-500 hover:bg-emerald-400
        focus:outline-none focus:ring-4 focus:ring-emerald-300/50
        text-slate-900 text-lg font-bold px-8 py-4 rounded-full
        transition-colors duration-200">Inscríbete</a>
  → Cada propiedad visual se declara explícitamente con una clase utilitaria.

Diferencia clave entre un framework de componentes y uno utility-first:
- Bootstrap (componentes): te da componentes y clases semánticas ya
  empaquetados (btn, card, navbar). Ahorra tiempo y garantiza consistencia,
  pero si quieres un botón fuera del diseño del framework necesitas
  sobrescribir variables o CSS propio.
- Tailwind (utility-first): te da clases atómicas (una propiedad por clase)
  y compones el diseño directamente en el HTML. Da control total y evita
  CSS muerto, pero el HTML es más verboso y el diseño se aprende leyendo
  clases.

¿Qué aprendí?
A prototipar una sección completa con Tailwind Play CDN sin instalar nada,
usando solo utilidades, y a contrastar el enfoque utility-first con el
enfoque de componentes de Bootstrap.

Versión: Rueda Nocturna — prototipo (nocturna/prototipo.html)

Búsqueda en output.css:
- bg-emerald-500 → SÍ aparece (la usamos en el botón principal).
- bg-pink-500 → NO aparece (no la usamos en ningún HTML).

¿Por qué? Tailwind es "on-demand": la CLI escanea los archivos HTML y
solo genera el CSS de las clases que encuentra escritas como strings.
bg-pink-500 no existe en index.html, así que no se genera.

1. Radios de borde:
   - rounded-full → botones y etiquetas.
   - rounded-2xl   → cards y contenedores.

   - p-6 en cards y contenedores; p-4 en alertas.
   - px-8 py-4 → botones grandes.
   - px-5 py-2.5 → botones pequeños de la card.
   - px-4 py-3 → inputs.

     bordes border-slate-800 / border-slate-700.

4. Tipografía:
   - Títulos: font-bold / font-extrabold + text-white.
   - Cuerpo: text-slate-300.
   - Secundario: text-slate-400 / text-slate-500.
   - Etiquetas y badges: text-xs uppercase tracking-widest.

5. Estados:
   - Hover: cambio de color de fondo.
   - Focus: focus:ring-4 con color a juego.
   - Transición: transition-colors duration-200 (o duration-300

6. Accesibilidad:
   - <label for> en cada input.
   - role="status" en la alerta de éxito.
   - Foco visible siempre (ring-4).
